# Система знаний команды

Учебный RAG-сервис по заданию [`1st_prompt.md`](1st_prompt.md). Пользователь добавляет документы `.txt`/`.md` или текст, задаёт вопрос и получает ответ с источниками либо отказ с `needs_review=true` и причиной. Поиск объединяет pgvector и BM25 через RRF; решение о достаточности оснований принимает backend.

## Запуск

1. Скопируйте `.env.example` в `.env` и задайте `YANDEX_FOLDER_ID`, `YANDEX_API_KEY`. Ключу нужен доступ к моделям AI Studio.
2. Выполните `docker compose up --build -d`.
3. Откройте `http://localhost/documents`. Проверка сервиса: `http://localhost/health`.

Контейнер API запускает Alembic-миграции перед Uvicorn. PostgreSQL хранится в томе `postgres_data`. Только Caddy публикует порт `80`; API и БД не имеют внешних портов. Для API оставлен исходящий сетевой доступ к Yandex AI Studio. Один Uvicorn worker нужен для единого BM25-индекса в памяти.

Пороги `EVIDENCE_MAX_COSINE_DISTANCE=0.78`, `EVIDENCE_MIN_BM25_SCORE=2.0` и `LLM_MIN_CONFIDENCE=0.7` заданы в `.env` и передаются контейнеру через Compose. Параметры chunking, top-K, RRF и модели тоже настраиваются там; доступные имена приведены в `.env.example`. После изменения `.env` выполните `docker compose up -d`, чтобы пересоздать API. Пороговая политика утверждена для учебного набора из пяти документов; при другом корпусе её следует перепроверить.

## Экспериментальная настройка поиска

Строки с `#` в `.env` — примеры: Compose их игнорирует, а приложение использует значения по умолчанию. Чтобы изменить параметр, уберите `#` в начале нужной строки и укажите число, например `VECTOR_TOP_K=8`. Затем выполните `docker compose up -d` и дождитесь ответа `http://localhost/health`. Меняйте по одному параметру за прогон, чтобы видеть его влияние.

| Параметр | По умолчанию | Что меняет |
|---|---:|---|
| `CHUNK_SIZE` | 1000 | Предельная длина фрагмента документа в символах. Меньшие фрагменты точнее выделяют факт, но теряют часть контекста; большие дают больше контекста и текста модели. Минимум — 8. |
| `CHUNK_OVERLAP` | 150 | Сколько символов конца предыдущего фрагмента повторять в следующем при разбиении длинного текста. Помогает сохранить контекст на границе; увеличивает объём индекса и повторы в результатах. Допустимый диапазон: от 0 до `CHUNK_SIZE - 3`. |
| `VECTOR_TOP_K` | 5 | Сколько ближайших фрагментов берёт семантический поиск pgvector. Большее значение расширяет список кандидатов, но добавляет менее близкие результаты. |
| `BM25_TOP_K` | 5 | Сколько фрагментов берёт поиск по словам BM25. Большее значение расширяет список кандидатов с совпадающими словами. |
| `FUSION_TOP_K` | 5 | Сколько первых фрагментов после объединения RRF попадёт в итоговый результат и контекст модели. Увеличение может повысить охват, но расходует больше входных токенов модели. |
| `RRF_K` | 60 | Константа формулы RRF `1 / (RRF_K + ранг)` для каждого из двух поисков. Большее значение сглаживает разницу между соседними рангами; балл RRF служит только для сортировки, не является вероятностью верного ответа. |

Все значения top-K и `RRF_K` должны быть положительными целыми числами. `CHUNK_SIZE` и `CHUNK_OVERLAP` действуют **при загрузке документа**: изменение `.env` не перестраивает уже сохранённые фрагменты и embeddings. Для сравнения нового разбиения загрузите исходные документы заново в отдельную тестовую базу. Остальные четыре параметра влияют на поиск по уже сохранённым фрагментам после пересоздания API.

Для сравнения используйте одни и те же документы и вопросы: сначала сохраните результат `docker compose exec -T api python -m scripts.diagnose --base-url http://api:8000`, затем измените один параметр и повторите команду. Смотрите на top-3, cosine distance, BM25 и совпадение фрагментов в обоих списках. После этого запустите `docker compose exec -T api python -m scripts.acceptance` и сравните ответы, источники и `needs_review`. Для контрольного набора исходные пороги evidence остаются `0.78` и `2.0`; изменение top-K или RRF может изменить первый фрагмент и тем самым решение о достаточности оснований. Порог `LLM_MIN_CONFIDENCE` относится уже к ответу модели, а не к retrieval.

## Контрольный набор и поиск

В `examples/demo_documents` лежат 5 вымышленных документов команды; вопросы и ожидаемая доступность ответа — в `examples/questions.json`. После настройки Yandex загрузите документы через UI либо выполните `docker compose exec -T api python -m scripts.diagnose --base-url http://api:8000 --load-fixtures`. Затем та же команда без `--load-fixtures` выводит top-3 по каждому вопросу с исходными диагностическими значениями. `--load-fixtures` добавляет документы в базу и при повторном запуске создаст дубликаты, поэтому используйте его один раз на чистой учебной базе.

После загрузки набора выполните `docker compose exec -T api python -m scripts.acceptance`. Скрипт читает `tests_data/kb_questions.jsonl` и проверяет семь ответов с источниками, три отказа с причиной, историю, аудит и экспорт. В `tests_data/kb_documents.jsonl` сохранены те же пять demo-документов в формате JSONL (`title`, `text`, `source_file`); загрузчик demo использует их исходные файлы из `examples/demo_documents`. `POST /kb/retrieve` остаётся диагностическим контрактом с телом `{"question":"Когда выпускают релизы?"}`. Число RRF показывает порядок, а не уверенность ответа. Результаты выполненной приёмки записаны в `openspec/changes/archive/2026-09-29-0001-team-knowledge-mvp/`.

## Примеры curl

Команды для Bash используют публичный адрес Caddy. Пример успешного вопроса рассчитан на пять загруженных demo-документов. В PowerShell используйте `curl.exe` и записывайте каждую команду в одну строку.

```bash
# Добавить документ
curl -sS -X POST http://localhost/kb/documents \
  -H 'Content-Type: application/json' \
  --data '{"title":"Памятка по доступу","text":"Заявку на доступ к репозиторию создаёт руководитель команды."}'

# Получить ответ с источником (после загрузки demo-набора)
curl -sS -X POST http://localhost/kb/ask \
  -H 'Content-Type: application/json' \
  --data '{"question":"Кто создаёт заявку на доступ к репозиторию?"}'

# Получить needs_review=true и причину
curl -sS -X POST http://localhost/kb/ask \
  -H 'Content-Type: application/json' \
  --data '{"question":"Какой бюджет у команды на обучение?"}'
```

## Хранение данных и проверка через psql

PostgreSQL хранит документы, фрагменты, историю вопросов и аудит в именованном томе Compose `postgres_data` (фактическое имя тома включает имя Compose-проекта). Доступ к БД есть только внутри Docker-сети. Посмотреть данные можно через контейнер `db`:

```bash
docker compose exec -T db psql -U kb -d kb -c "SELECT id, title, created_at FROM documents ORDER BY id DESC LIMIT 10;"
docker compose exec -T db psql -U kb -d kb -c "SELECT id, question, needs_review, review_reason FROM qa_runs ORDER BY id DESC LIMIT 10;"
docker compose exec -T db psql -U kb -d kb -c "SELECT id, action, entity_id, details FROM audit_runs ORDER BY id DESC LIMIT 10;"
```

`GET /kb/history` показывает последние 50 вопросов. `GET /kb/history/export` скачивает **всю** историю вопросов как `qa_history.json`; ссылка находится на странице `/history`. Экспорт записывает событие `history.exported` с числом выгруженных записей в `audit_runs`.

## Воспроизводимая ручная проверка

Выполняйте сценарий на чистой тестовой базе: `--load-fixtures` добавляет документы повторно и не подходит для уже заполненной базы.

1. Запустите `docker compose up --build -d` и убедитесь, что `http://localhost/health` возвращает `{"status":"ok"}`.
2. Один раз загрузите пять документов: `docker compose exec -T api python -m scripts.diagnose --base-url http://api:8000 --load-fixtures`. Проверьте, что `GET /kb/documents` содержит пять записей.
3. Выполните `docker compose exec -T api python -m scripts.acceptance`. Ожидается `10/10` и `история/аудит/экспорт=PASS`.
4. На странице `/questions` задайте вопрос «Кто создаёт заявку на доступ к репозиторию?». Проверьте ответ «руководитель команды» и источник `01_onboarding`.
5. Задайте вопрос «Какой бюджет у команды на обучение?». Проверьте статус «Нужна проверка», причину и отсутствие источников.
6. На странице `/history` откройте фильтр требующих проверки и скачайте JSON. Убедитесь, что обе записи есть в файле, а в `audit_runs` появилась запись `history.exported`.

## Known limitations / Известные ограничения

В текущем MVP hybrid retrieval выполняется по исходному вопросу одним поисковым запросом: semantic search через pgvector и lexical search через BM25 объединяются с помощью RRF.

Такая схема хорошо работает для вопросов, ответ на которые содержится в одном или нескольких хорошо ранжируемых фрагментах, однако имеет ограничение для составных вопросов.

Во время расширенного тестирования был обнаружен случай, где один вопрос требовал одновременно определить категорию инцидента и найти отдельные условия отката релиза. Фрагмент с первой частью ответа попал в контекст, а фрагмент с условиями rollback остался за пределами retrieval top-K. Evidence gate при этом признал найденный контекст достаточным, поэтому модель сформировала корректный, но неполный ответ.

Простое увеличение глубины поиска повышает recall, но одновременно увеличивает размер контекста и количество нерелевантных или архивных фрагментов. Поэтому параметры retrieval для MVP были оставлены без дальнейшей подгонки под тестовый набор.

Возможные направления развития:

- decomposition составного вопроса на несколько атомарных подзапросов;
- multi-query retrieval с последующим объединением результатов;
- отдельная проверка полноты evidence по каждой части вопроса.

Эти механизмы сознательно оставлены за пределами MVP.

## API документов

- `GET /kb/documents` — список.
- `POST /kb/documents` — JSON `{"title":"...","text":"..."}`; документ появляется только после успешной индексации.
- `GET /kb/documents/{id}` — исходный текст.
- `DELETE /kb/documents/{id}` — удаление документа и его snippets.
- UI поддерживает вставку текста и UTF-8 файлы `.txt`/`.md`.

## API вопросов и истории

- `POST /kb/ask` и `POST /ai/answer_with_sources` — JSON `{"question":"..."}`; возвращают `answer`, `sources` с цитатами, `needs_review`, `review_reason`, `diagnostics`, `run_id`.
- `GET /kb/history` — последние 50 ответов; `?needs_review=true` оставляет требующие проверки.
- `GET /kb/history/export` — скачивание всей истории вопросов в JSON; операция фиксируется в аудите.
- `GET /kb/audit` — последние 50 событий добавления/удаления документов и вопросов.
- Панель `/questions` показывает ответ, источник и причину проверки; `/history` — историю и аудит.

OpenAPI: `http://localhost/docs`. При отсутствии ключа или сбое Yandex загрузка/поиск вернут ошибку, документы частично не сохраняются.

## Локальные проверки

`python -m compileall -q app migrations scripts tests` и `docker compose config --quiet`. Unit-тесты с зависимостями контейнера: `docker compose exec -T api python -m unittest discover -s tests -v`. Интеграционный тест БД без вызова Yandex: `docker compose exec -T api python -m scripts.smoke`.
